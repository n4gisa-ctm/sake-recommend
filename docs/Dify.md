# Dify API 連携ガイド

このアプリはバックエンドを持たず、ブラウザから直接 Dify のチャットボットAPIを呼び出します。
連携に必要なのは **①API URL** と **②APIシークレットキー** の2つだけです。

## 手順1: Dify 側で API 情報を取得する

1. [Dify](https://cloud.dify.ai/) にログインし、作成済みの**チャットボットアプリ**（チャットフロー/エージェント）を開く
2. 左メニューの **「APIアクセス」**（英語UIでは *API Access*）を開く
3. 画面上部に表示される **APIサーバー** の URL を控える
   - Difyクラウド版なら `https://api.dify.ai/v1`
   - セルフホスト版なら `https://あなたのドメイン/v1`
4. 右上の **「APIキー」** ボタン →「新規シークレットキーを作成」→ `app-` で始まるキーをコピー
   - ⚠️ キーは**アプリごと**に発行されます。連携したいチャットボットアプリの画面から発行してください

## 手順2: アプリに設定する（2通り）

### 方法A: `.env` ファイル（推奨）

ユーザーに設定画面を見せず、すぐチャットを始められます。

1. `sake-recommend` フォルダ直下に `.env` ファイルを作成（`.env.example` のコピーでOK）:

```
VITE_DIFY_API_URL=https://api.dify.ai/v1
VITE_DIFY_API_KEY=app-xxxxxxxxxxxxxxxxx
```

2. **開発サーバーを再起動**する（Viteは起動時にしか `.env` を読みません）:

```bash
npm run dev
```

- `.env` は `.gitignore` 済みなので GitHub にはアップされません
- Netlify / Vercel にデプロイする場合は、各サービスの管理画面の「環境変数」に同じ2つを登録してからビルドします

### 方法B: アプリ内の設定画面（フォールバック）

`.env` がない場合、初回起動時に設定画面が表示されます。上記の URL とキーを入力すれば、ブラウザの localStorage に保存されて次回以降は不要です。

## 手順3: 動作確認

1. アプリを開き「日本酒を探してみる」→ チャット画面へ
2. サジェストのどれかを押して、AIの返答がストリーミング表示されれば連携成功
3. エラーが出る場合は下の表を参照

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| `Dify API error 401: Access token is invalid` | APIキーの間違い。`app-` で始まるシークレットキーか、コピーミスがないか確認 |
| `Dify API error 404` | URLの間違い。末尾が `/v1` になっているか確認（`/v1/chat-messages` まで書かない） |
| `Dify API error 400: Agent Chat App does not support blocking mode` 等 | アプリ種別の不一致。本アプリはストリーミング優先なので通常は発生しないが、出た場合はDify側のアプリ種別を確認 |
| 返答が来ない / quota エラー | Dify無料プランのメッセージ数上限（200回/月程度）に達した可能性。Dify側の利用状況を確認 |
| `.env` を書いたのに設定画面が出る | 開発サーバーの再起動忘れ。変数名の `VITE_` プレフィックス漏れも確認 |

## 仕組み（参考）

- 呼び出しているのは `POST {API_URL}/chat-messages`（[src/lib/dify.ts](../src/lib/dify.ts)）
- `response_mode: streaming` で SSE を受信し、1文字ずつ表示。非対応環境ではJSON一括受信にフォールバック
- `conversation_id` を保持して会話の文脈を継続。「新しい会話」でリセット

## セキュリティ上の注意

フロントエンドから直接呼ぶ構成のため、**APIキーはビルド成果物（ブラウザ）から取り出せます**。
個人利用・限定公開なら実用上問題になりにくいですが、広く公開する場合は:

1. Dify のアプリ設定でレート制限を設定する
2. 将来的には Netlify Functions / Cloudflare Workers などの薄いプロキシを挟み、キーをサーバー側に隠す

ことを推奨します（要件定義書の将来課題）。
